# Divergence log

Where the implementation departs from `docs/BUILD_PLAN.md` or
`docs/TECHNICAL_ARCHITECTURE.md`, and why. Required by BUILD_PLAN Part 0 item 6.

| #   | Document                        | Says                                                                                                | We did                                                                                                                                                                                            | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Technical Architecture §3.1–3.2 | `PayoutOutcome`, `PayoutAcknowledgement` and `CallbackTrigger` live in `packages/adapters`          | They live in `packages/domain/src/provider/outcomes.ts`, and `packages/adapters` re-exports them                                                                                                  | `packages/ledger` must accept a `PayoutOutcome` (§3.2) but must not depend on the adapter layer. Putting the types in `domain` keeps the dependency graph acyclic without weakening the type-level guarantee, which was the point of the section.                                                                                                                                                                                                                                                                                                    |
| D2  | Build Plan 1.1                  | `Money` with a currency registry                                                                    | `Money<C extends CurrencyCode>` — the currency is a type parameter                                                                                                                                | The plan requires that "cross-currency arithmetic must be impossible to express". A runtime check alone makes it _detectable_, not impossible. The type parameter makes `rub.add(ngn)` a compile error, with the runtime check retained for values whose currency is only known dynamically.                                                                                                                                                                                                                                                         |
| D3  | Build Plan 1.2                  | Account type `FLOAT_RUB` etc.                                                                       | Same nine types, plus an explicit `partition` field on every account                                                                                                                              | Guardrail G8 requires partition awareness from day one. Adding it later would mean migrating every account row.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| D4  | Build Plan, general ordering    | One step per branch, one PR per step                                                                | Phases delivered on a single development branch, in phase order, with one commit per step                                                                                                         | Requested by the project owner for this engagement so the platform can be demonstrated end to end. The per-step DoD is still evidenced per commit. Revert to one-PR-per-step once the team is more than one engineer.                                                                                                                                                                                                                                                                                                                                |
| D5  | Technical Architecture §2.4     | Payout failure posts `DR FLOAT_NGN / CR USER_PAYABLE`                                               | Payout failure posts nothing                                                                                                                                                                      | That posting presumes `USER_PAYABLE` was debited when the payout was _initiated_. We debit only on a `SETTLED` outcome, so on failure the liability is already correct and any "reversal" would imply a posting that never happened. The refund path moves the value explicitly, with its own approval.                                                                                                                                                                                                                                              |
| D6  | Build Plan 0.5                  | `pnpm dev` boots the stack via Docker Compose                                                       | `pnpm stack:up` prefers Compose and falls back to natively installed PostgreSQL and Redis                                                                                                         | Some development environments have no reachable Docker daemon. The Compose files remain the deployment artefact.                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| D7  | Technical Architecture §2.4     | Settlement is booked through `PARTNER_RECEIVABLE` on both legs, with `FX_PNL` absorbing the residue | Send currency: `DR PARTNER_RECEIVABLE / CR FLOAT` then `DR USER_PAYABLE / CR PARTNER_RECEIVABLE`. Destination currency: `DR FLOAT / CR USER_PAYABLE`, then `DR USER_PAYABLE / CR FLOAT` on payout | Booking the residue to `FX_PNL` on every transfer leaves a permanent debit balance in one currency and a permanent credit in another, growing with volume, which is not what an FX P&L account means. Discharging the sender's liability against the settlement receivable closes both currencies' books exactly. `FX_PNL` is now used only where there is a genuine FX difference — a settlement rate that differs from the quoted rate — which is the correct semantic. The full sequence is in `apps/api/src/transfers/transfer-saga.service.ts`. |
| D8  | Build Plan 12.1                 | "Repository-level separation of PII stores"                                                         | Separation is a Nest module (`PartitionsModule`) that exports only the gateway, plus schema separation in the database                                                                            | The CI boundary check caught `app.module.ts` importing the partition repositories to register them for injection. Wrapping them in a module that exports only the gateway removes the reason for anyone outside `src/partitions/` to import one, so the check enforces a rule the architecture already makes natural.                                                                                                                                                                                                                                |
| D9  | Build Plan 5.5                  | "Generated OpenAPI spec committed"                                                                  | Also served at `/docs` and `/openapi.json` by the API                                                                                                                                             | A committed file satisfies the DoD but is not reachable during a demonstration or by a partner integrating against us. The viewer is self-contained — no CDN, so it works behind a proxy and needs no hole in the CSP.                                                                                                                                                                                                                                                                                                                               |
